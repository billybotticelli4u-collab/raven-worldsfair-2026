Raven Scout — how to read what you'll get back

  

    
A current receipt-v1 returns signed evidence: findings, coverageGaps, and rulesVersion; observation and freshness data in slot, timestamp, and maxAgeSeconds; and verification fields payloadHash, receiptId, signerPublicKey, and signature.

    
When something cannot be checked, the receipt says what was and was not observed through explicit findings and coverage gaps. If the evidence required to issue a receipt cannot be established, the service refuses instead of returning a silent pass.

    
Raven never says "safe". If coverage gaps remain, the honest answer is: not enough evidence for a full pass — and the receipt will list exactly which gaps those are.

  

  

    
Raw request:

    
curl -X POST https://raven-hosted-verifier.onrender.com/receipt/v1 \
  -H "x-api-key: $KEY" -H "content-type: application/json" \
  -d '{"mintAddress":"<mint>","tokenProgramAddress":"<program>"}'

    
MCP: npx -y raven-verify-mcp → tool raven_verify_token (config). Contract: openapi.json.

    
Receipt: verify signature (ed25519, domain raven-receipt/v1) over payloadHash using signerPublicKey, check the receiptId binding, then match signerPublicKey to the independently authenticated pin. The current handoff may name the signer as keyId rvk_c2997e90215279c2 outside the receipt-v1 wire; /pubkey is a cross-check, never the trust root — full recipe.

    
coverageGaps is normative: anything listed there was NOT evaluated. A receipt with no listed finding triggered and gaps remaining means "no findings on checked surfaces", never "safe".
